<objective>
Rewrite `app/shared/gatekeeper.py` from its current 100%-dead, async, unbounded-wait design
into a synchronous rate limiter safe to call from the worker's blocking 2-3s-interval loops,
and wire it into every outbound Claude and Meta WhatsApp API call. This is Phase 4 decision 2:
the user explicitly wants real rate limiting (chose rewrite over deletion).

Purpose: no external API call may run unrate-limited, and no rate-limit wait may block the
worker past its next scheduled poll (the concrete failure mode of the old async design under
`BlockingScheduler` + `max_instances=1`).
Output: a synchronous `ApiGatekeeper` with a small bounded wait + `RateLimitExceeded`, wired
into `ai_service.py`'s 3 Claude call sites and `whatsapp_meta.py`'s 4 senders.
</objective>

  <name>Task 1: Rewrite gatekeeper.py as a synchronous, bounded-wait rate limiter</name>
  <files>app/shared/gatekeeper.py, tests/unit/test_gatekeeper.py</files>
  <action>
    Rewrite `app/shared/gatekeeper.py` from scratch (keep `_load_rate_config()` and
    `_ServiceBucket`'s sliding-window logic — `is_allowed()`/`record()`/`current_rpm`/
    `current_rph` — unchanged in behavior, but `_ServiceBucket.__init__` no longer needs to
    read `retry_after_seconds`/`max_retries` from the config dict since the new design doesn't
    use them):

    1. Add `class RateLimitExceeded(RuntimeError):` — raised when a service is still
       rate-limited after the bounded wait.
    2. Add module-level constants `_MAX_WAIT_SECONDS = 1.5` and `_POLL_INTERVAL_SECONDS = 0.2`
       — independent of `config/rate_limits.json`'s `retry_after_seconds` (10s/30s), which
       stays in the config file as documentation of target limits for a human tuning them, but
       must NOT drive a sleep duration inside a 2-3s-interval worker loop (see
       04-RESEARCH.md's "Pitfall 1"). Do not modify `config/rate_limits.json`.
    3. `ApiGatekeeper.execute(self, service, api_call, *args, max_wait=_MAX_WAIT_SECONDS,
       poll_interval=_POLL_INTERVAL_SECONDS, **kwargs)` — fully synchronous (no `asyncio`, no
       `await`, no coroutine detection):
       ```python
       def execute(self, service, api_call, *args, max_wait=_MAX_WAIT_SECONDS,
                   poll_interval=_POLL_INTERVAL_SECONDS, **kwargs):
           bucket = self._bucket(service)
           waited = 0.0
           while not bucket.is_allowed() and waited < max_wait:
               time.sleep(poll_interval)
               waited += poll_interval
           if not bucket.is_allowed():
               log.warning("gatekeeper: %s still rate-limited after %.2fs wait (rpm=%d/%d) — failing fast",
                           service, waited, bucket.current_rpm, bucket.rpm)
               raise RateLimitExceeded(f"{service} rate limit exceeded after {waited:.2f}s wait")
           bucket.record()
           t0 = time.monotonic()
           result = api_call(*args, **kwargs)
           log.info("gatekeeper: %s OK elapsed=%.2fs rpm=%d/%d", service, time.monotonic() - t0,
                    bucket.current_rpm, bucket.rpm)
           return result
       ```
       No internal retry-on-failure loop — `api_call`'s exceptions propagate directly (the old
       code's `max_retries`-with-backoff loop is deleted entirely; retry/defer is already
       handled one layer up by the outbox's `attempts`/`max_attempts` and by `ai_service`'s
       existing fallback-on-exception path — see 04-RESEARCH.md's Gatekeeper Design section for
       the full reasoning).
    4. Keep `get_queue_status()` unchanged. Keep the module-level `gatekeeper = ApiGatekeeper()`
       singleton at the bottom.
    5. Update the module docstring to explain the sync rewrite and why (mirror the reasoning
       above — the old async unbounded wait was incompatible with `BlockingScheduler`'s
       `max_instances=1` + 2-3s poll intervals, see `app/worker.py`).

    Rewrite `tests/unit/test_gatekeeper.py` for the sync API — remove the `run()`/`asyncio`
    helper entirely and every `run(gk.execute(...))` wrapper; call `gk.execute(...)` directly.
    Remove `test_execute_calls_async_function` (async callables are no longer supported —
    document this if useful, but no caller in this codebase passes one). Remove
    `test_execute_retries_on_failure` and `test_execute_raises_after_max_retries_exhausted`
    (retries are gone); replace with `test_execute_does_not_retry_and_propagates_exception`:
    a callable that always raises should have `execute()` raise immediately with call_count
    staying at 1 (no retry). Keep the bucket tests (`TestServiceBucket`) as-is except drop
    `retry_after`/`max_retries` kwargs from `_make_bucket()`'s config dict if now unused. Keep
    `test_get_queue_status_returns_dict`, `test_unknown_service_uses_default_bucket`,
    `test_load_missing_config_returns_empty_gatekeeper` (adjusted to call `execute()` directly,
    no `run()`). Add a new test `test_execute_raises_rate_limit_exceeded_after_bounded_wait`:
    build a gatekeeper with a very small `rpm=1`, call `execute()` once to consume the bucket,
    then call it again with a small `max_wait` (e.g. `max_wait=0.3, poll_interval=0.05`) and
    assert it raises `RateLimitExceeded` — measure elapsed time and assert it's roughly bounded
    (e.g. `elapsed < max_wait + 0.3`) so this pins the "never stalls indefinitely" contract
    without being flaky.
  </action>
