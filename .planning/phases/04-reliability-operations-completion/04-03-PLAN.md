  <name>Task 1: Automated proof that SQLAlchemyJobStore persists across a restart</name>
  <files>tests/integration/test_scheduler_persistence.py</files>
  <action>
    Create `tests/integration/test_scheduler_persistence.py`. Open with a module docstring
    explaining: this test verifies the SQLAlchemyJobStore mechanism `app/worker.py` relies on
    (`SQLAlchemyJobStore(url=Config.DATABASE_URL)`) genuinely persists job scheduling state
    across independent scheduler instances — i.e. across what a worker process restart looks
    like — using a local sqlite file as the backing store (same SQLAlchemy jobstore code path
    Postgres would use, no live Supabase/Railway credentials needed). The live production
    check (DATABASE_URL actually set on Railway with the Supabase Session Pooler connection
    string) is a separate operator checkpoint — see plan 04-07.

    Use `apscheduler.schedulers.background.BackgroundScheduler` (not `BlockingScheduler` —
    `start()`/`shutdown()` return immediately, `BlockingScheduler.start()` would hang the test)
    and `apscheduler.jobstores.sqlalchemy.SQLAlchemyJobStore`. Use pytest's `tmp_path` fixture
    for an isolated sqlite file per test run.

    Test 1 — `test_job_next_run_time_survives_scheduler_restart`:
    1. `db_url = f"sqlite:///{tmp_path / 'jobstore.db'}"`.
    2. Build scheduler A: `BackgroundScheduler(jobstores={"default": SQLAlchemyJobStore(url=db_url)})`,
       `scheduler_a.start()`, add a cron job mirroring `app/worker.py`'s real monthly_report job
       shape: `scheduler_a.add_job(lambda: None, "cron", day=1, hour=8, minute=0,
       id="monthly_report", replace_existing=True)`.
    3. Read back `job_a = scheduler_a.get_job("monthly_report")`, capture
       `next_run_time_a = job_a.next_run_time` (assert it is not None).
    4. `scheduler_a.shutdown(wait=False)` — simulates the worker process ending.
    5. Build scheduler B as a brand-new instance pointed at the SAME `db_url` (this is the
       "restart": a new process would re-read the same on-disk store), `scheduler_b.start()`.
    6. `job_b = scheduler_b.get_job("monthly_report")` — assert it is not None, and assert
       `job_b.next_run_time == next_run_time_a` (the exact same scheduling state survived,
       independent of the Python process that created it).
    7. `scheduler_b.shutdown(wait=False)`.

    Test 2 — `test_job_store_is_isolated_per_database` (control case, guards against a false
    positive from in-process caching): repeat steps 2-3 with scheduler A against `db_url`, then
    build scheduler C against a DIFFERENT, freshly-created empty sqlite file in the same
    `tmp_path`; assert `scheduler_c.get_job("monthly_report")` returns `None` — proving Test 1's
    persistence is genuinely coming from the shared on-disk store, not some other cache.

    Confirm `apscheduler` and `sqlalchemy` are already available (both are already in
    `requirements.txt` per `app/worker.py`'s existing imports) — no new dependency needed.
  </action>
  <verify>`python -m pytest tests/integration/test_scheduler_persistence.py -q` — both tests pass, no leftover scheduler threads (each test shuts down every scheduler it starts).</verify>
  <done>An automated test proves job scheduling state (next_run_time) genuinely persists across two independent SQLAlchemyJobStore-backed scheduler instances sharing one on-disk database, and that this isn't a false positive from in-process state.</done>

    ```
    # --- Worker job-store persistence (APScheduler) ---
    # Postgres connection string so scheduled jobs (e.g. the monthly report cron) survive a
    # worker restart. Use the Supabase SESSION POOLER string (port 5432, host
    # aws-<region>.pooler.supabase.com, user postgres.<project-ref>) — NOT the "Direct
    # connection" string (db.<ref>.supabase.co), which is IPv6-only and will not resolve on
    # Railway's default IPv4-only outbound networking. Must start with postgresql:// (not
    # postgres://) — SQLAlchemy 2.0 rejects the old scheme. Get it from: Supabase Dashboard →
    # Settings → Database → Connection string → Session pooler. Without this set, the worker
    # falls back to an in-memory job store (scheduling state is lost on every restart).
    DATABASE_URL=
    ```
    In `CLAUDE.md`'s "Env Vars Reference" table, add a row:
    `| \`DATABASE_URL\` | prod | Postgres Session Pooler connection string — persists the
    APScheduler job store across worker restarts (see .env.example for the exact shape) |`
