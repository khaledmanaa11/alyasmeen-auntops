# Plan: Phase 4 — Database Security Surface

**Goal**: Make the Supabase access surface a deliberate security decision by formalizing the RPC functions in migrations, restricting them to the `service_role`, and documenting the rationale for server-side-only access.

## Success Criteria
1. The `run_query` and `run_exec` RPC functions are defined in a versioned migration.
2. The functions are restricted so they cannot be called by the `anon` or `authenticated` roles (public web/mobile clients).
3. The application is confirmed to use the `service_role` key (or a key with equivalent restricted access).
4. A security test verifies that the `anon` key cannot execute arbitrary SQL.

## Tasks

### 1. Migration: Formalize and Restrict RPCs
- **Goal**: Bring "shadow" RPC functions into the migration system and lock them down.
- **Action**: Create `supabase/migrations/20260615230000_secure_rpc.sql`.
- **Content**:
    - `CREATE OR REPLACE FUNCTION run_query(sql text) RETURNS json ...`
    - `CREATE OR REPLACE FUNCTION run_exec(sql text) RETURNS void ...`
    - `REVOKE ALL ON FUNCTION run_query(text) FROM public, anon, authenticated;`
    - `REVOKE ALL ON FUNCTION run_exec(text) FROM public, anon, authenticated;`
    - `GRANT EXECUTE ON FUNCTION run_query(text) TO service_role;`
    - `GRANT EXECUTE ON FUNCTION run_exec(text) TO service_role;`
- **Verification**: Run `supabase db reset` (or equivalent) to ensure migrations apply.

### 2. Configuration & Documentation
- **Goal**: Clarify that the `service_role` key is required for the application to function.
- **Action**: 
    - Update `.env.example` to rename `SUPABASE_KEY` to `SUPABASE_SERVICE_ROLE_KEY` (or add a comment).
    - Update `app/services/config.py` if necessary to clarify intent (though it just reads from env).
    - Update `PROJECT.md` or `ARCHITECTURE.md` with the security rationale.
- **Rationale**: Since the app is a trusted server-side process, using `service_role` and disabling `anon` RPC access provides a clean security boundary. RLS is not used because all access is funneled through the server.

### 3. Security Validation Test
- **Goal**: Empirically prove that the `anon` key is insufficient to execute SQL.
- **Action**: Create `tests/integration/test_security_surface.py`.
- **Steps**:
    1. Initialize a Supabase client with the `anon` key.
    2. Attempt to call `run_query("SELECT 1")`.
    3. Assert that the call fails with a 403 Forbidden or similar permission error.
    4. Initialize with `service_role` key and assert success.

## Risks & Mitigations
- **Risk**: Changing the key in production might break the app if not updated in the environment.
- **Mitigation**: The migration doesn't *change* the key, it changes the *permissions* required by the key. We must ensure the production environment uses the `service_role` key before applying the migration.
- **Risk**: `SECURITY DEFINER` vs `SECURITY INVOKER`.
- **Mitigation**: Use `SECURITY DEFINER` for these specific RPCs but restrict `GRANT` to only `service_role`. This allows the functions to perform their tasks while ensuring only our trusted server can call them.
