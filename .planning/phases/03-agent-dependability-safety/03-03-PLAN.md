<objective>
Make AI failure visible, and give Claude a real escalation tool.

Purpose — two problems, one file:

1. **The AI-failure fallback is dead code in production.** `processor.handle_message` wraps
   `generate_reply()` in a try/except that sets `AI_FALLBACK_REPLY`
   (`app/services/processor.py:370-380`), and a test exercises it — but only by
   monkeypatching `generate_reply` itself. In production that `except` can never fire,
   because `generate_reply` wraps its *entire* body in its own try/except and always returns
   a string (`app/services/ai_service.py:444-446`). A real Claude outage therefore reaches
   the customer as a second, near-duplicate Arabic apology that is indistinguishable from a
   normal reply — and no handoff can ever be triggered from it. This plan makes unrecoverable
   AI failure a distinguishable exception so plan 03-05 can escalate on it.
2. **Deterministic keyword matching cannot catch most escalation-worthy messages.** The
   dataset's real handoff cases (ids 23, 35, 57, 63) are angry/complaint/privacy messages
   with no "give me a human" vocabulary in them at all. Claude can judge those; it needs a
   tool to act on that judgement, so the escalation is a durable DB row rather than a
   sentence it made up.

Output: `AIUnavailableError`, a raise-instead-of-swallow contract, and the fifth tool
`request_human_handoff` (definition only — its execution lives in `processor.py`, wired in
plan 03-05, per the one-AI-file rule and ADR-005).
</objective>

  <files>app/services/ai_service.py, tests/unit/test_ai_service.py</files>
  <action>
**(a) Define the exception**, near the top of `app/services/ai_service.py` after the imports:

```python
class AIUnavailableError(RuntimeError):
    """Raised when generate_reply cannot produce a real model reply.

    Deliberate contract change (Phase 3): this function used to swallow every
    exception and return a hard-coded Arabic apology, which made a genuine
    Claude outage indistinguishable from a normal answer — so the caller could
    never escalate to a human. The caller (processor.handle_message) is now
    responsible for BOTH the customer-facing fallback text AND opening a
    handoff. The customer must still always get a reply; see plan 03-05.
    """
```

**(b) Replace the three swallow points in `generate_reply`:**

1. `if not ai_available(): return "عذرًا، الخدمة غير متاحة حالياً..."` (line 355-356) ->
   `raise AIUnavailableError("CLAUDE_API_KEY missing or anthropic SDK unavailable")`.
   A bot that cannot reach Claude at all is exactly the situation the aunt needs to know
   about. This does **not** cause an alert storm: `handoff.trigger()` is idempotent per
   phone (plan 03-01) and, once a handoff is open, `handle_message` returns early on the
   paused check (plan 03-04) — so a key-less deployment produces one handoff per customer,
   not one per message.
2. The outer `except Exception:` (lines 444-446) ->
   ```python
   except AIUnavailableError:
       raise
   except Exception as exc:
       log.exception("Claude API error")
       raise AIUnavailableError(str(exc)) from exc
   ```
   Keep the `log.exception` — the structured error detail is still wanted.
3. `return "\n".join(parts).strip() or "(no reply)"` (line 443) -> if the joined text is
   empty, `raise AIUnavailableError("empty model response")`. Shipping the literal
   `"(no reply)"` to a customer over WhatsApp is a defect, and an empty completion is a real
   (if rare) failure mode worth a human's attention.

**(c) Do NOT change the inner tool-execution try/except** at lines 412-416. A single failing
tool turning into a `tool_result` string that Claude talks around is correct behaviour and
must survive: one broken tool should not cost the customer their whole reply. Add a comment
saying so, since it now reads as inconsistent with the new outer contract.

**(d) Update the docstring** of `generate_reply`: it now documents that the function raises
`AIUnavailableError` and no longer returns a fallback string, and that `tool_executor`
receives five tools.

**(e) Fix the tests that encode the old contract.** In `tests/unit/test_ai_service.py`,
`test_returns_fallback_when_no_api_key` (line 107) asserts a string comes back with no API
key. Rewrite it as `test_raises_when_no_api_key` using `pytest.raises(ai.AIUnavailableError)`.
Add:
- `test_raises_when_anthropic_call_fails` — monkeypatch the client so `messages.create`
  raises; assert `AIUnavailableError` and that the original exception is chained
  (`excinfo.value.__cause__ is not None`).
- `test_raises_when_response_has_no_text` — a fake response whose `content` blocks carry no
  `.text`; assert `AIUnavailableError` and that `"(no reply)"` is nowhere in the codebase's
  runtime path any more.
- `test_failing_tool_does_not_break_the_reply` — a `tool_executor` that raises; assert
  `generate_reply` still returns the model's final text.

Then grep the rest of the suite for anything else depending on the string-return-on-failure
behaviour (`grep -rn "no reply\|صار خلل مؤقت" tests/ app/`) and fix or remove those
expectations. `processor.AI_FALLBACK_REPLY` stays — it becomes the *only* AI fallback string
in the codebase, which was previously duplicated across the two modules.
