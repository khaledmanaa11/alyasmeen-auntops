<objective>
Create `app/services/policy.py`: the deterministic gate that every AI-proposed tool action
passes through before execution (success criterion 1), plus the deterministic
Arabic+English escalation detector that plan 03-04 wires into `handle_message`.

Purpose: today `_make_tool_executor`'s closure (`app/services/processor.py:393-411`) hands
Claude's tool arguments straight to the tool implementations with no validation layer at
all. Some invariants happen to hold by construction (`add_to_cart` has no `price` argument
to override; no tool can touch `orders.status`) — this plan turns those implicit facts into
explicit, unit-tested rules so a carelessly-added sixth tool cannot quietly break them.

Output: one pure module, zero I/O, and a test file that pins every rule.

**Design constraint that shapes the whole module: `policy.py` performs no I/O.** It does not
import `app.db.database`, `app.routers.whatsapp_helpers`, `app.services.processor`, or
`app.services.handoff`. The catalog and the order status arrive through the `context`
argument, supplied by the caller that already has them. Two reasons, both load-bearing:
(a) it keeps the gate genuinely deterministic and trivially unit-testable, and (b) this
codebase binds DB helpers at import time, so a `catalog` imported here would become yet
another seam every future test file has to remember to patch or else silently hit the LIVE
production database (`tests/conftest.py` module docstring; Pitfall 1 in 03-RESEARCH.md).
</objective>

```python
from __future__ import annotations
```

**Constants**

```python
# Canonical clamp range for AI-supplied cart quantities. processor.py holds
# duplicate literals today (MIN_CART_QTY/MAX_CART_QTY, processor.py:39-40);
# plan 03-05 replaces those with an import from here so there is one source.
MIN_CART_QTY = 1
MAX_CART_QTY = 50

MIN_ADDRESS_CHARS = 10      # "رام الله" alone is not a deliverable address
MAX_ADDRESS_CHARS = 300
MAX_CATEGORY_CHARS = 60
MAX_REASON_CHARS = 200

# Every tool ai_service.py exposes, and what it is allowed to touch.
#   read      — no writes at all
#   cart      — mutates the in-session cart only
#   customer  — mutates the customer/session record
#   escalation— opens a handoff
#   order     — would mutate an existing order (NOTHING has this scope today)
TOOL_SCOPES = {
    "add_to_cart":          "cart",
    "show_menu":            "read",
    "get_order_status":     "read",
    "save_address":         "customer",
    "request_human_handoff":"escalation",
}

# Success criterion 4: the agent may only act on an order that is still being
# prepared. Once the aunt has moved it past to_do, agent mutation is refused.
AGENT_MUTABLE_ORDER_STATUSES = frozenset({"to_do"})
```

Add a prominent comment above `TOOL_SCOPES` recording *why* the "order" scope exists with
no members: order creation happens only through the hard-coded `confirm` path
(`processor.py:327-329` -> `_handle_confirm` -> `create_order_atomic`), and status
progression happens only in the operator-authenticated
`app/routers/ui_api.py::api_update_status`. The AI has never had a way to mutate an order.
The scope + the gate below make that a *rule* instead of an accident, so a future sixth tool
is denied by default rather than allowed by omission.

**Decision type**

```python
@dataclass(frozen=True)
class PolicyDecision:
    allowed: bool
    code: str = "ok"          # machine reason: unknown_tool, session_paused,
                              # product_not_in_catalog, address_too_short,
                              # order_not_mutable, ...
    message: str = ""         # Arabic text handed back to Claude as the tool_result
    args: dict = field(default_factory=dict)   # normalised args to execute with
    escalate: bool = False    # a denial that should also open a handoff
```

**`validate(tool_name: str, args: dict | None, context: dict) -> PolicyDecision`**

`context` keys (all optional except where noted, with safe defaults):
- `paused: bool`
- `catalog: list[dict]` — rows shaped `{"name", "list_price", ...}` exactly as
  `whatsapp_helpers.catalog()` returns them
- `order_status_provider: Callable[[], str | None]` — called **only** for order-scoped
  tools, so no DB read happens for the five tools that exist today
- `phone: str` (for logging only)

Rules, evaluated in this order (first denial wins):

1. **session_paused** — if `context.get("paused")`: deny, `escalate=False`, message
   `"المحادثة محوّلة لحنان حالياً 🌿"`. A human owns this conversation; the agent does not
   get to keep mutating state underneath her.
2. **unknown_tool** — `tool_name not in TOOL_SCOPES`: deny, `escalate=True`, message
   `"هذا الطلب بحاجة لمتابعة من حنان."` Default-deny is the point: an unrecognised tool name
   is either a model hallucination or a tool someone added without updating the policy.
3. **order_not_mutable** — if `TOOL_SCOPES[tool_name] == "order"` and
   `order_status_provider()` returns a status not in `AGENT_MUTABLE_ORDER_STATUSES`: deny,
   `escalate=True`, message
   `"طلبك تجاوز مرحلة التحضير، رح أحوّلك لحنان تتابع معك 🌿"`. (Unreachable with today's five
   tools — pinned by a test that registers a synthetic order-scoped tool.)
4. **Per-tool argument rules**, each returning normalised `args` on allow:
   - `add_to_cart`: resolve `product_name` via `resolve_product(name, catalog)` (below). No
     match -> deny, `code="product_not_in_catalog"`, `escalate=False`, message
     `f"لم أجد منتجاً باسم '{name}' في القائمة."` (identical wording to
     `processor.py:433`, so the customer-visible behaviour does not change). Match ->
     allow with `args = {"product_name": <canonical catalog name>, "qty": <clamped int>}`.
     Quantity: coerce with `int()`, fall back to 1 on `TypeError`/`ValueError`, clamp to
     `MIN_CART_QTY..MAX_CART_QTY`. **Never take a price from `args`** — there is no price
     field in the tool schema (`ai_service.py:225-244`) and there must never be one; note
     that in a comment so a future edit does not add one.
   - `show_menu`: coerce `category` to `str`, strip, truncate to `MAX_CATEGORY_CHARS`.
     Never denied.
   - `get_order_status`: always allow, empty args (read-only).
   - `save_address`: strip `address`; deny if shorter than `MIN_ADDRESS_CHARS` with
     `code="address_too_short"`, `escalate=False`, message
     `"وين بالضبط؟ اكتبي المدينة والحي والشارع لو سمحتِ 🙏"` (the wording already in the
     tool description at `ai_service.py:293`). Truncate at `MAX_ADDRESS_CHARS`.
   - `request_human_handoff`: always allow; normalise `reason` to a stripped string
     truncated to `MAX_REASON_CHARS`, defaulting to `"طلب الزبونة"` when empty. This tool is
     the escape hatch — it must never be the thing that gets blocked.

**`resolve_product(product_name: str, catalog: list[dict]) -> dict | None`**

Exact case-insensitive name match first, then substring match — the same two-pass strategy
`_tool_add_to_cart` uses at `processor.py:419-430`, extracted here so the grounding rule and
the execution use one definition. `_tool_add_to_cart` keeps its own lookup (the numeric
menu-pick path at `processor.py:353-362` calls it directly, bypassing the AI and therefore
the policy gate); passing the canonical name through means it hits the exact-match branch.
Note that intentional double-lookup in a comment.

No logging framework needed in this module — it returns decisions, the caller logs them.

Add to the same module:

```python
def detect_handoff_keyword(text: str) -> str | None:
```

Returns one of `"explicit_human"`, `"complaint"`, `"refund"`, `"damaged"`, `"privacy"`, or
`None`. Plan 03-04 maps any non-None result to `handoff.trigger(phone, "keyword_request", ...)`.

Structure the vocabulary as a module constant so tests and future edits have one place to
look:

```python
# Multi-word phrases are matched as substrings; single tokens are matched
# against whitespace/punctuation-delimited words ONLY.
HANDOFF_PHRASES: dict[str, tuple[str, ...]] = {...}   # substring match
HANDOFF_WORDS:   dict[str, tuple[str, ...]] = {...}   # whole-word match
```

Suggested vocabulary, derived from the real phrasing in
`tests/data/whatsapp_agent_dataset.json` (ids 23, 35, 45, 57, 63 are the escalation-worthy
cases — read them before finalising the list):

- `explicit_human`
  - phrases: `"احكي مع"`, `"أحكي مع"`, `"بدي حدا"`, `"بدي أحكي"`, `"بدي احكي"`,
    `"مع حنان"`, `"مش بوت"`, `"مو بوت"`, `"مش روبوت"`, `"شخص حقيقي"`,
    `"talk to a human"`, `"talk to someone"`, `"speak to a human"`, `"real person"`,
    `"customer service"`, `"customer support"`
  - words: `"موظف"`, `"موظفة"`, `"انسان"`, `"إنسان"`, `"human"`, `"agent"`, `"operator"`
- `complaint`
  - phrases: `"بدي اشتكي"`, `"بدي أشتكي"`
  - words: `"شكوى"`, `"شكوي"`, `"اشتكي"`, `"complaint"`, `"complain"`
- `refund`
  - phrases: `"بدي مصاري"`, `"رجعولي"`, `"ردولي"`, `"money back"`, `"my money"`
  - words: `"استرجاع"`, `"إسترجاع"`, `"ارجاع"`, `"إرجاع"`, `"refund"`, `"chargeback"`, `"فلوسي"`
- `damaged`
  - words: `"مكسور"`, `"مكسورة"`, `"تالف"`, `"تالفة"`, `"broken"`, `"damaged"`, `"defective"`
- `privacy`
  - phrases: `"من وين رقمي"`, `"مين انتو"`, `"مين أنتو"`, `"how did you get my number"`
  - words: `"خصوصية"`, `"privacy"`

**Two rules that are not optional, both about false positives:**

1. **Never match a bare `"بشر"` or any short token that is a substring of an ordinary
   product-conversation word.** `"بشر"` is a substring of `"بشرتي"` ("my skin"), which is
   one of the most common things a customer says to a skincare bot — `tests/unit/test_processor.py`
   even drives `"بشرتي جافة كثير"` through the pipeline. That single token would escalate a
   large fraction of normal conversations. This is why single tokens go through whole-word
   matching and only multi-word phrases use substring matching.
2. **`"حنان"` (the aunt's name) is only matched inside a phrase** (`"مع حنان"`,
   `"احكي مع"`), never as a bare word — `"شكراً حنان"` is a thank-you, not an escalation.

Implementation: lowercase the input, normalise Arabic-Indic digits away is unnecessary, but
DO split on a regex of whitespace + common punctuation (`[\s،,.!؟?:;()"'`] and the Arabic
comma) to build the word set for whole-word matching. Check phrases against the lowercased
full string. Iterate groups in a fixed order (`explicit_human`, `refund`, `damaged`,
`complaint`, `privacy`) so the return value is deterministic when a message matches two
groups.

Add a short module comment recording the scope decision: `opt_out_of_messages` (dataset id
54) is deliberately **out of scope for this phase** — there is no consent/suppression
mechanism anywhere in this codebase, and routing a do-not-contact request into the aunt's
manual handoff queue would mis-handle a compliance request rather than honour it. Tracked as
follow-up work outside Phase 3.
