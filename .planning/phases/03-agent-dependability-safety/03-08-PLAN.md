<objective>
Prove the requirements this phase carries but did not have to build, pin success criterion 4
end-to-end, and write the durable knowledge down.

Three of Phase 3's nine requirements — REQ-bot-aunt-notification, REQ-sched-followup,
REQ-sched-retry-queue — were satisfied by Phase 4's outbox rewrite rather than by anything
in this phase. Research confirmed each against current code. But "confirmed by reading the
code once in August 2026" is not the same as "cannot silently regress": there is no test
asserting the aunt's new-order alert goes through the outbox, and `retry_queue.py` was
deleted with only a migration comment recording it. This plan converts those three
verifications into tests.

It also closes the phase's documentation debt. `CLAUDE.md` still describes an architecture
that predates the outbox (it claims the aunt notification is a bare try/except send), and
the `ALYASMEEN/wiki/` vault has no page for `processor.py`, `gatekeeper.py`, `handoff.py`,
`audit.py`, or anything Phase 3 built — the project's own rules say a meaningful change ends
with a vault update so the next session inherits the knowledge instead of rediscovering it.

Output: a requirements test file, a new vault page, and an accurate project brief.
</objective>

- `test_confirm_queues_an_aunt_notification_through_the_outbox` — monkeypatch
  `Config.AUNT_PHONE`, build a cart, drive `handle_message(phone, "confirm")`, and assert

  it proves the alert is durable and retried, not fire-and-forget.
- `test_aunt_notification_contains_order_number_and_total`
- `test_customer_confirmation_is_not_lost_if_the_aunt_alert_fails` — make the aunt's

`TestFollowupsAreDurable` (REQ-sched-followup)
- `test_followup_enqueues_instead_of_sending_directly` — assert
  `app/services/followup.py` calls `queue_text` and that `send_text` is never invoked
  (spy on both).
- `test_followup_job_is_registered_in_the_worker` — import `app.worker` and assert the
  follow-up job is scheduled. Keep this structural (inspect the module source or the job
  registration list); do not start a real scheduler.

`TestRetryQueueIsRetired` (REQ-sched-retry-queue)
- `test_no_retry_queue_module_exists` — `importlib.util.find_spec("app.services.retry_queue")`
  is None, same for `retry_actions`.
- `test_no_retry_queue_job_in_the_worker` — `"retry" not in app/worker.py`'s job registrations.
- `test_outbox_poller_is_the_retry_mechanism` — a job that fails is retried up to
  `max_attempts` and then marked `failed` with `notify_permanent_failure` called. (Trim if
  `tests/unit/test_processor.py` already covers this; cross-reference it in a comment rather
  than duplicating the assertion.)

`TestAgentCannotMutateOrders` (success criterion 4, end-to-end)
- `test_ai_tool_surface_has_no_order_mutating_tool` — over `ai_service._TOOLS`: no tool name
  or input-schema property mentions `status`, `cancel`, `refund`, or `delete`.
- `test_policy_tool_scopes_cover_every_ai_tool` — `{t["name"] for t in _TOOLS} == set(policy.TOOL_SCOPES)`
  (the duplicate of 03-02's guard, kept here because this is the file a future reader opens
  when asking "how do I know the agent can't cancel an order?").
- `test_order_status_writes_come_only_from_the_operator_api` — this is a source-level
  architectural-boundary guard with **two separate assertions**, because `processor.py`
  legitimately calls the order-creation RPC (that is the only way an order is ever created)
  while it must never touch order-status mutation directly:
  1. **Status-progression boundary.** Grep the `app/` tree for the literal
     `UPDATE orders SET status`. Every hit must live in `app/routers/ui_api.py` or under
     `app/db`/`supabase/migrations` — never in `processor.py`, `ai_service.py`, or
     `policy.py`. This is the boundary that says "only the operator dashboard API moves an
     order between statuses".
  2. **Order-creation boundary.** Grep the `app/` tree for the `create_order_atomic` RPC
     call (`rpc("create_order_atomic"` or however it is invoked). It is legitimately called
     from `processor.py`'s `_handle_confirm` — that is the sole path that creates an order,
     always landing it in `to_do` (03-01/03-05 territory) — but assert it is called from
     **nowhere else**: not from `ai_service.py`, not from `policy.py`, and not from any other
     function in `processor.py`. The invariant being pinned is "the agent can trigger order
     creation only through the one hard-coded confirm path it does not control the wording
     of, and can never trigger a status change at all" — not "processor.py never touches
     orders".
  A source-level assertion is unusual, but it is the only way to pin an architectural
  boundary that is currently maintained by nothing but habit — add a comment explaining that
  and what to do if either boundary legitimately needs to change.
- `test_confirm_creates_orders_only_in_to_do` — after `_handle_confirm`, the created order's
  status is `to_do`.
  </action>
