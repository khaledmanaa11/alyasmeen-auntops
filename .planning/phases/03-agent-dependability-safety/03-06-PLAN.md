<objective>
Build the release-gate evaluation REQ-prod-eval-gate actually asks for, and measure a real
baseline with it.

What exists today is `tests/data/eval_intent.py`: a mature standalone script that calls the
Claude API with a *bespoke intent-classification prompt* over a 56,000-row noisy dataset. It
is useful prior art but it does not satisfy the requirement — it is not pytest, it has no
pass/fail semantics, and above all it evaluates a side-channel prompt rather than the
production code path, so it cannot catch a tool-call regression, a policy-gate false
positive, or a handoff that fails to fire. Those are exactly the regressions this phase
introduces the risk of.

Purpose: turn "does the agent behave" into a command that exits non-zero. This plan builds
the harness and **measures**; plan 03-07 sets the thresholds from what is measured. No
numbers are invented — no baseline has ever been recorded against `handle_message` in this
repo, so any threshold picked before the first run would be a guess.

Output: `tests/eval/`, an `eval` pytest marker excluded from the default run, and
`03-EVAL-BASELINE.md` containing real measured numbers.
</objective>

  <name>Task 1: The behaviour map — what each of the 75 cases should actually do</name>
  <files>tests/eval/__init__.py, tests/eval/expected_behavior.py, tests/unit/test_eval_dataset.py</files>
  <action>
`tests/data/whatsapp_agent_dataset.json` has 75 entries with `id` (int 1-75), `raw_input`,
`expected_intent` (63 distinct values, mostly unique), `language_profile`, `entities`, and
`edge_case_tags`. It has **no** `expected_tool` or `expected_handoff` field — there is no
mapping from those labels to what `handle_message` should do. That map is the missing piece,
and at 75 rows it is small enough to hand-author once, carefully.

Create `tests/eval/__init__.py` (empty) and `tests/eval/expected_behavior.py`:

```python
OUTCOMES = frozenset({
    "add_to_cart", "show_menu", "get_order_status", "save_address",
    "handoff",   # any handoffs row opened, by any of the five triggers
    "no_tool",   # a conversational reply with no tool call and no handoff
})

# case id -> the set of outcomes that count as CORRECT. A set, not a single
# value, because several cases have more than one defensible right answer:
# "بدي كريم لبشرتي الجافة" is fine as either show_menu or a clarifying question.
EXPECTED: dict[int, frozenset[str]] = { ... all 75 ids ... }

# Cases deliberately not graded, each with a written reason.
UNSCORED: dict[int, str] = { ... }

# Tiers drive per-tier thresholds in plan 03-07 (a wrong answer is not
# equally costly everywhere).
TIERS: dict[str, frozenset[int]] = {"critical": ..., "handoff": ..., "informational": ...}
```

**Read the dataset before authoring this — do not infer from intent names alone.** Guidance:

- `critical` tier — the order path. Intents like `create_order*`, `select_menu_item*`,
  `update_cart_quantity`, `view_cart`, `clear_cart`, `confirm_order`,
  `set_fulfillment_*`, `resume_abandoned_cart_and_checkout`. A wrong tool here directly
  breaks an order.
- `handoff` tier — must escalate. At minimum ids 23 (damaged jar), 35 (week-old order +
  complaint), 45 (explicit "talk to Hanan"), 47 (voice note), 57 (refund threat), 63
  (privacy), 67 (sticker), plus `wholesale_inquiry`, `request_deferred_payment`,
  `create_custom_bulk_order_and_check_price`, `cancel_order`,
  `modify_order_add_item_post_checkout`, `report_damaged_item_and_request_resolution`,
  `duplicate_third_party_order`, `submit_payment_proof`, `wrong_recipient` — everything the
  agent has no tool for and must not improvise. `cancel_order` and
  `modify_order_add_item_post_checkout` belong here specifically because of success
  criterion 4: the agent must hand those to a human, never fake them.
- `informational` tier — FAQ-ish (`check_product_ingredients`, `request_store_info`,
  `check_payment_methods`, `check_delivery_cost_and_time`, `check_restock_date`, greetings,
  thanks, `positive_feedback`, `price_objection`). Mostly `no_tool` or `show_menu`.
  **`app/data/knowledge/` is empty in this repo**, so several of these have no grounded
  answer available and will score poorly for reasons Phase 3 does not own. Grade them, but
  keep them in their own tier so a single global threshold cannot block a release on them —
  and say so in a comment.
- `UNSCORED`: `opt_out_of_messages` (id 54 — explicitly out of scope for this phase, see
  03-02), plus anything genuinely ambiguous. Keep this list short and justify every entry;
  an eval that excuses its own failures is worthless.
- Media cases (`unsupported_media_*`, `order_by_image_reference`) expect `handoff` — that is
  what plan 03-04's `handle_unsupported_media` does. Note in a comment that these are driven
  through `process_event` with a synthetic media payload, not `handle_message`, since a text
  placeholder like `[ملصق]` is not what the pipeline actually receives in production.

**Then write `tests/unit/test_eval_dataset.py`** — a fast, API-free test that runs in the
DEFAULT suite (no marker):
- every dataset id appears in exactly one of `EXPECTED` or `UNSCORED`
- every `EXPECTED` value is a non-empty subset of `OUTCOMES`
- `TIERS` partitions the scored ids with no overlap and no orphans
- the dataset file still parses and still has 75 entries with the expected keys

This is the cheap guard that keeps the map honest as the dataset evolves, and it costs
nothing to run.
  </action>
  <verify>

**(a) Marker + double guard.** In `pyproject.toml`, add an `eval` marker and change
`addopts` to `-m "not integration and not eval"`. Note in a comment that `integration` is
currently registered but unused by any test, so `eval` gets its own marker rather than
sharing one — someone running `pytest -m integration` must not accidentally spend money.

In `tests/eval/conftest.py`, add a session-level guard that `pytest.skip`s the whole
directory unless **both** hold:
- `os.environ.get("RUN_AGENT_EVAL") == "1"`
- `Config.CLAUDE_API_KEY` is set

Marker + env var + key means the eval is unreachable from `pytest -q`, from `pytest tests/`,
and from `pytest -m integration`. Only a deliberate invocation runs it.

**(b) Keep the database fake, let Claude be real.** `tests/conftest.py`'s autouse `mock_db`
and `block_live_db` fixtures apply to `tests/eval/` too — that is exactly what we want: the
eval must exercise the real prompt, the real tool loop, the real policy gate and the real
handoff triggers, but it must never write to the production Supabase project. `generate_reply`
is not patched by conftest, so the Anthropic call goes out for real.

**One gotcha will silently ruin the results if missed.** `ai_service._full_catalog_context()`
(`ai_service.py:95-123`) builds the `<catalog>` block the whole system prompt is grounded on,
and it swallows any exception and returns `""`. Under `block_live_db` the catalog read fails,
so the eval would run against an **empty catalog** — every `add_to_cart` case would fail for
reasons having nothing to do with the agent. Fix it at the one seam that feeds both consumers:

```python
@pytest.fixture(autouse=True)
def eval_catalog():
    import app.ai.retriever as retriever
    retriever._CATALOG = EVAL_CATALOG          # rows: sku(str-int), name, price, description, tags, aliases
    retriever._CATALOG_LOADED_AT = time.monotonic()
    yield
    retriever.invalidate_catalog()
```

Injecting `retriever._CATALOG` works for BOTH paths because `_catalog()` reads the module
global at call time: `ai_service` imports `_catalog` inside the function body, and
`whatsapp_helpers` bound the function object (not the value) at import. Also patch
`processor.catalog` to `whatsapp_helpers.catalog` semantics if any test needs it directly.
`EVAL_CATALOG` must use numeric-string `sku` values — `whatsapp_helpers.catalog()` does
`int(r["sku"])` and skips rows that fail (`whatsapp_helpers.py:29-33`). Use 6-8 realistic
ALYASMEEN-style products (creams, lotions, candles) with Arabic names.

**(c) Outcome capture.** In `tests/eval/test_agent_eval.py`:

```python
def run_case(case, fake_db, sent_messages, flush_outbox, monkeypatch) -> dict:
```
- fresh random phone per case (so sessions/handoffs never bleed between cases)
- wrap `processor._make_tool_executor` so the returned closure records every
  `(name, args)` into a list before delegating — the least invasive capture point, and it
  sees post-policy dispatch
- text cases: `processor.handle_message(phone, case["raw_input"], "زبونة")`
- media cases (`unsupported_media_*`, `order_by_image_reference`): build a Meta payload with
  the right `type` and run `processor.process_event(...)`
- `flush_outbox()`, then read the reply from `sent_messages`
- derive the observed outcome, in this precedence order:
  1. a handoffs row exists for the phone -> `"handoff"`
  2. a tool was called -> the last tool name
  3. otherwise -> `"no_tool"`
- also record: reply non-empty, reply language matches the case's language profile
  (reuse `ai_service.detect_language`), the tool args, and elapsed seconds
- wrap each case in try/except so one exploding case does not abort the run; record it as an
  error outcome

**(d) Sampling and cost control.** `EVAL_SAMPLES` (default `12`) and `EVAL_SEED` (default
`20260828`) from the environment. Sample **stratified** across the three tiers with
`random.Random(seed)` so a 12-case run always covers critical and handoff cases, never 12
greetings. `EVAL_SAMPLES=0` or `all` means the full 75. Each case is 1-2 Haiku calls with a
~2k-token system prompt: a 12-case run is roughly 20 calls, well under $0.05; the full 75 is
still cents. Put the cost estimate in the module docstring the way `eval_intent.py` does.

**(e) The test itself** — one `@pytest.mark.eval` test that runs the sample, prints a
readable per-tier report (`-s` shows it), writes machine-readable results to
`tests/eval/.last_run.json` (gitignored), and — **for this plan only** — asserts nothing
beyond "the harness ran and produced a result for every sampled case". Thresholds are plan
03-07's job; a gate asserting invented numbers before a baseline exists would either always
pass or block the phase for no reason. Say that in a comment so the missing assertion does
not look like an oversight.
  </action>

  <done>The eval harness drives real `handle_message`/`process_event` calls against a faked DB and a real Claude, samples deterministically, and cannot be triggered by any default or accidental pytest invocation.</done>
