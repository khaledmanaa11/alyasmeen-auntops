<objective>
Turn the measured baseline into an actual gate — a command that fails when the agent gets
worse (success criterion 3).

Purpose: 03-06 measured what the agent does today. This plan encodes "don't ship something
worse than that" and writes down how a human runs it. Framing matters: this is a **regression
gate against a measured baseline**, not an absolute quality bar. Nobody has an authoritative
number for "how accurate should an Arabic WhatsApp skincare bot be", and the stale
`RESEARCH-3.md` proposal that used to be quoted here was explicitly unvalidated guesswork.
What is defensible is "measurably worse than last week is a release blocker".

Deliberately **not** in scope: a CI workflow. This repo has no `.github/` at all; inventing
a pipeline solely to host this gate would be a larger change than the requirement asks for.
The gate is a documented local command, per the phase's own decisions.

Output: threshold assertions in the eval test, and `docs/EVAL_GATE.md`.
</objective>

<task type="auto">
  <name>Task 1: Regression thresholds derived from the measured baseline</name>
  <files>tests/eval/test_agent_eval.py</files>
  <action>
Add, next to the `BASELINE_*` constants 03-06 recorded:

```python
# A release gate, not a quality bar. Thresholds are the MEASURED baseline
# minus a tolerance that absorbs model non-determinism and sampling noise —
# every case is a live Claude call at temperature 0.3, so two runs of the same
# sample legitimately differ by a case or two.
TOLERANCE = {
    "critical":      0.05,   # order path — tightest, a regression here loses orders
    "handoff":       0.05,   # a missed escalation means an angry customer talks to a bot
    "informational": 0.15,   # loosest: app/data/knowledge/ is empty, these are noisy by construction
    "overall":       0.08,
}
MIN_SAMPLE_FOR_TIER_GATE = 5   # below this a tier's percentage is noise, report only
```

Then make the `@pytest.mark.eval` test assert:
1. `overall >= BASELINE_OVERALL - TOLERANCE["overall"]`
2. per tier, `tier_score >= BASELINE_BY_TIER[tier] - TOLERANCE[tier]`, **skipped for any
   tier with fewer than `MIN_SAMPLE_FOR_TIER_GATE` sampled cases** in this run (a default
   12-case sample cannot meaningfully gate a tier it drew 2 cases from — report the number,
   do not fail on it).
3. A hard floor independent of the baseline: **every sampled case must produce a non-empty
   reply to the customer.** This one is absolute, not relative. "The customer always gets a
   reply" is a phase invariant (locked decision 1), not something allowed to degrade by 8%.
4. Assert no case errored out (the try/except outcome from 03-06's `run_case`) — an
   exception in the pipeline is a bug, not a score.

**Failure output is the deliverable, not the assertion.** Use `pytest.fail` with a built
multi-line message containing: the per-tier table (baseline / measured / tolerance /
verdict), and then every regressed case as
`id | intent | expected {…} | observed X | raw_input (truncated)`. A gate that prints
"assert 0.71 >= 0.79" tells the person nothing about what to fix. Build the report string
before asserting so it prints on success too (under `-s`).

Also add `test_gate_constants_are_consistent` — a **default-suite** (unmarked, API-free)
test asserting `set(TOLERANCE) == set(BASELINE_BY_TIER) | {"overall"}`, that every tolerance
is in `0..0.5`, and that `BASELINE_MEASURED_AT` is present. This keeps the constants from
rotting silently and costs nothing.
  </action>
  <verify>
```
pytest -q                                          # default suite green, no API calls
RUN_AGENT_EVAL=1 EVAL_SAMPLES=12 pytest -m eval tests/eval -q -s
```
The gate run passes and prints the per-tier table. Then confirm it can actually fail:
temporarily lower a `BASELINE_BY_TIER` entry's counterpart (e.g. set `TOLERANCE["overall"]`
to `-1.0`) and re-run — the test must fail and the report must list the regressed cases.
Revert afterwards and state in the SUMMARY that the failure path was exercised.
  </verify>
  <done>The eval exits non-zero on regression below baseline-minus-tolerance, exits non-zero if any customer got no reply, and prints an actionable per-case report either way.</done>

<task type="auto">
  <name>Task 2: docs/EVAL_GATE.md — the documented pre-release procedure</name>
  <files>docs/EVAL_GATE.md</files>
  <action>
New file, written for Khaled running it before a release — same practical register as
`docs/BACKUP_DRILL.md`. Sections:

1. **What this gate checks.** The real `handle_message`/`process_event` pipeline against 75
   labeled Arabic/English customer messages: which tool fired, whether a handoff opened,
   whether the customer got a reply. Explicitly contrast with `tests/data/eval_intent.py`,
   which is a different tool measuring a different thing (a side-channel classification
   prompt over noisy inputs) and is **not** the release gate — someone will otherwise find
   that script and assume it is.

2. **When to run it.** Before any release that touches `ai_service.py`, `processor.py`,
   `policy.py`, `handoff.py`, the system prompt, the tool definitions, or `CLAUDE_MODEL`.
   Not needed for template/CSS/dashboard-only changes.

3. **The command** (both shells, since this project is developed on Windows):
   ```bash
   RUN_AGENT_EVAL=1 pytest -m eval tests/eval -q -s              # 12-case sample, ~$0.02
   RUN_AGENT_EVAL=1 EVAL_SAMPLES=all pytest -m eval tests/eval -q -s   # full 75, before a big release
   ```
   ```powershell
   $env:RUN_AGENT_EVAL=1; pytest -m eval tests/eval -q -s
   ```
   State plainly that it costs real money, that `pytest -q` never runs it, and why it is
   guarded by both a marker and an env var.

4. **Reading the output.** How to read the per-tier table; what the three tiers mean and why
   `informational` has a looser tolerance (empty `app/data/knowledge/`).

5. **What to do when it fails.** A decision list: (a) a real behaviour regression — fix the
   code, do not touch the baseline; (b) a bad expectation in `expected_behavior.py` — fix
   the map and re-run; (c) genuine model drift after a `CLAUDE_MODEL` bump — re-baseline
   deliberately (procedure below); (d) noise on a small sample — re-run with
   `EVAL_SAMPLES=all` before concluding anything.

6. **Re-baselining.** The explicit procedure: run the full 75, update `BASELINE_*` in
   `test_agent_eval.py` **and** `.planning/phases/03-agent-dependability-safety/03-EVAL-BASELINE.md`,
   and commit both in one commit whose message states why. Add the rule in bold: **lowering
   a baseline is a decision that must be visible in the diff** — never quietly widen a
   tolerance to make a red gate green.

7. **Known limitations.** Small dataset (75 cases); no CI (no `.github/` in this repo — the
   gate is a human step, and Phase 6 go-live is where automating it would belong); the
   database is faked during the eval, so it validates agent behaviour, not Supabase
   integration; `informational` scores are capped by the empty knowledge directory.

Then add a one-line pointer to this file from `docs/TODO.md`'s pre-release checklist if such
a checklist exists there; if not, skip rather than inventing one.
  </action>
