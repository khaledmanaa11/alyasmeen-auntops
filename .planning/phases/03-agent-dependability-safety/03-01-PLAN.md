```python
    "unsupported_media": "أرسلت رسالة صوتية أو صورة أو ملصق",

    "operator_takeover": "تدخّل يدوي من لوحة التحكم",

```

Change the import line to also bring in `execute_returning`:
`from app.db.database import execute, execute_returning, query`
(`execute_returning` is the existing INSERT…RETURNING seam, `app/db/database.py:158-166`;
it is deliberately not retried, which is correct for a write.)

Then add:

```python
def trigger(phone: str, reason: str, metadata: dict | None = None,
            assigned_to: str = "aunt", notify: bool = True) -> str:
```

Behaviour, in this order:

1. **Idempotency.** `query("SELECT id FROM handoffs WHERE phone = %s AND status = 'active' ORDER BY created_at DESC LIMIT 1", (phone,))`.
   If a row comes back: re-assert the pause (step 3 below — cheap, and it self-heals a row
   whose pause was lost), log `handoff_already_active`, and return that existing id
   **without** inserting a second row, writing a second audit entry, or re-notifying the
   aunt. There is no unique constraint stopping duplicate active rows
   (`idx_handoffs_status` is a plain partial index, `supabase/migrations/20260614000001_durable_messaging.sql:57`)
   — this function is the only thing preventing an alert storm when a customer sends five
   angry messages in a row.

2. **Insert.** `execute_returning("INSERT INTO handoffs (phone, reason, status, assigned_to, metadata) VALUES (%s, %s, 'active', %s, %s) RETURNING id", (phone, reason, assigned_to, metadata or {}))`
   and read `row["id"]`. Same column shape `app/routers/ui_api.py:126-129` already inserts.
   `handoffs.phone` has a live FK to `customers(phone)` — every caller must have upserted
   the customer first; document that in the docstring as the caller's responsibility.

3. **Pause the session — as an UPSERT, not an UPDATE.**
   ```sql
   INSERT INTO sessions (phone, paused) VALUES (%s, TRUE)
   ON CONFLICT (phone) DO UPDATE SET paused = TRUE, updated_at = now()
   ```
   `resolve()` can use a bare `UPDATE` because a session row provably exists by the time a
   handoff is resolved. `trigger()` can NOT: the very first message from a brand-new
   customer may be a voice note (plan 03-04's media path), which reaches here before
   `save_session()` has ever run for that phone. A bare `UPDATE` would silently no-op and
   the bot would keep replying to a customer it had just "handed off".

4. **Audit.** Lazy `from app.services import audit` inside the function body (the same
   cycle-avoidance pattern `resolve()` uses at line 56), then
   `audit.log_action("bot", "handoff_triggered", {"handoff_id": ..., "phone": phone, "reason": reason})`.
   Wrap in try/except — `log_action` is already best-effort, but the lazy import itself can
   theoretically fail.

5. **Notify the aunt** via `_notify_aunt(phone, reason, handoff_id)` (task 2). Only when
   `notify=True`.

6. Return the handoff id.

**Error contract:** steps 1-3 (the durable state) must be allowed to RAISE. Do not wrap
them in a swallow-everything try/except — a handoff nobody can see is worse than a loud
failure, and `app/db/database.py` already gives these calls retry + circuit breaking. Steps
4-5 (audit, notification) are best-effort and must never take the handoff down with them.
The plans that call `trigger()` from the message pipeline (03-04, 03-05) are responsible
for wrapping the call so the customer still gets a reply — say so explicitly in the
docstring.

Keep the whole function synchronous and DB-only. No sleeps, no HTTP: this runs inside the
worker's `BlockingScheduler` job (`app/shared/gatekeeper.py:1-27` explains why blocking
work here skips poll ticks).

**(a) `_notify_aunt(phone, reason, handoff_id)` in `app/services/handoff.py`.**

```python
def _notify_aunt(phone: str, reason: str, handoff_id: str) -> None:
```
- Wrap the entire body in try/except, logging `handoff_notify_failed` on error. A failing
  notification must never undo the handoff that already succeeded.
- **Loop guard (mandatory, same as `notify_permanent_failure`):** return immediately if
  `phone` is `Config.AUNT_PHONE` or `Config.ADMIN_PHONE`. Handing off a conversation with
  the aunt's own number and then WhatsApping her about it is an outbox loop.
- Return if `Config.AUNT_PHONE` is falsy.
- Look up the display name: `query("SELECT name FROM customers WHERE phone = %s", (phone,))`,
  falling back to the raw phone number when the name is empty (exactly what
  `notify_permanent_failure` does at lines 108-110).
- Build the message from `REASON_LABELS.get(reason, reason)`:
  `f"🙋 {label} — {label_name}\nافتحي تبويب «محادثات» بلوحة التحكم للرد، ولما تخلصي اضغطي «أعد للبوت».\nhttps://wa.me/{phone.lstrip('+')}"`
  (plain Arabic, tells her exactly what to do — the same voice 05-08's alert cards use).
- Send it with a lazy `from app.services import processor` **inside the function**, then
  `processor.queue_text(Config.AUNT_PHONE, msg)`. The lazy import is not optional: from
  plan 03-04 onward `processor` imports `handoff`, so a module-level import here is a
  circular import. Never call `send_text` directly — `queue_text` is the durable outbox and
  is the only sanctioned send path from the message pipeline
  (`app/services/processor.py:46-54`).
- Import `Config` from `app.services.config` at module top (handoff.py does not import it yet).
