      Leave no stub `trigger()` behind: an empty function that looks implemented is worse than

    All DB access goes through `from app.db.database import query, execute` with `%s`
    placeholders (project rules 3 and 6).

    ```python
    def resolve(handoff_id: str, resolved_by: str) -> bool:
        """Return the conversation to the bot. Idempotent: returns False if the
        handoff does not exist or is already resolved."""
    ```
    Implementation order matters:
    1. `SELECT id, phone, status FROM handoffs WHERE id = %s` — return False if missing or
       `status != 'active'`.
    2. `UPDATE handoffs SET status = 'resolved', resolved_at = now(),
        metadata = COALESCE(metadata, '{}'::jsonb) || jsonb_build_object('resolved_by', %s)
        WHERE id = %s AND status = 'active'`
    3. `UPDATE sessions SET paused = FALSE WHERE phone = %s` — this is the "return to bot" half;
       without it the bot stays muted forever. Do this even if the customer has no session row
       (a no-op UPDATE is fine).
    4. `audit.log_action(resolved_by, "handoff_resolved", {"handoff_id": ..., "phone": ...})`
       (Task 2 creates `audit.log_action`; import it lazily inside the function to avoid an
       import cycle if Phase 3's module later imports audit too).
    5. Return True.

    ```python
    def active_count() -> int:
        """SELECT COUNT(*) FROM handoffs WHERE status = 'active' — powers the nav badge."""

    def bot_recently_active(phone: str, window_minutes: int = 5) -> dict | None:
        """Bot-vs-aunt conflict detection. Returns {'last_activity': iso, 'paused': bool}
        when the bot has written to chat_history for this phone within the window,
        else None."""
    ```
    `bot_recently_active` must stay a cheap heuristic — one
    `SELECT MAX(created_at) AS last_at FROM chat_history WHERE phone = %s AND role = 'assistant'`
    plus `SELECT paused FROM sessions WHERE phone = %s`. Add a comment: the failure mode this
    guards is *a human and a bot* overlapping on one customer, not two concurrent humans, so
    row versioning / advisory locks / a distributed lock manager would be wildly
    disproportionate for a 10-30 orders/day shop. Define `CONFLICT_WINDOW_MINUTES = 5` as a
    module constant.

    **`tests/unit/test_handoff_resolve.py`** — monkeypatch the `query`/`execute` names bound
    into `app.services.handoff` with an in-memory fake (same technique as
    `tests/unit/test_operator_sessions.py`). Cover: resolve on an active handoff returns True
    and issues both the handoffs UPDATE and the `sessions ... paused = FALSE` UPDATE; resolve on
    an already-resolved handoff returns False and issues NO update; resolve on a missing id
    returns False; `active_count` returns the count; `bot_recently_active` returns None when the
    last assistant message is older than the window and a dict when it is inside it.
  </action>
  <verify>`python -m pytest tests/unit/test_handoff_resolve.py -q` passes; `grep -n "def trigger" app/services/handoff.py` returns nothing if the file was created by this plan (or returns Phase 3's untouched implementation if it already existed).</verify>

  <name>Task 2: app/services/audit.py — operator action trail</name>
  <files>app/services/audit.py, tests/unit/test_audit.py</files>
  <action>
    Create `app/services/audit.py` over the EXISTING `audit_logs` table
    (`id, actor, action, details JSONB, created_at`). Do not add a migration.

    ```python
    OPERATOR_ACTIONS = (
        "login_success", "login_failed", "logout", "logout_all",
        "session_revoked", "mfa_enrolled", "mfa_reset", "password_reset_requested",
        "order_status_changed", "order_status_conflict_override",
        "product_created", "product_updated", "product_toggled", "product_deleted",
        "broadcast_sent", "handoff_resolved",
        "alert_retried", "alert_retry_all",
    )

    def log_action(actor: str, action: str, details: dict | None = None) -> None
    def list_operator_actions(limit: int = 200) -> list[dict]
    ```

    `log_action` inserts `INSERT INTO audit_logs (actor, action, details) VALUES (%s, %s, %s)`
    and must be **best-effort**: wrap the write in try/except and log a structlog warning on
    failure. An audit write failing must never break the operator action it is recording —
    losing one trail row is strictly better than a 500 on a status change. Also log a structlog
    warning if `action not in OPERATOR_ACTIONS` (still write it — the allowlist governs the
    read side, not what may be recorded).

    `list_operator_actions` must filter to the allowlist. `audit_logs` predates this phase and
    already carries rows written by the `create_order_atomic` Postgres function where `actor` is
    a **customer's phone number** — showing those in the operator trail would mix customer
    activity into "who did what". Filter on `action`, not on the shape of `actor`. Build the
    placeholder list from the constant, never from user input:
    ```python
    placeholders = ", ".join(["%s"] * len(OPERATOR_ACTIONS))
    sql = f"SELECT id, actor, action, details, created_at FROM audit_logs WHERE action IN ({placeholders}) ORDER BY created_at DESC LIMIT %s"
    rows = query(sql, (*OPERATOR_ACTIONS, limit))
    ```
    (The f-string interpolates only a generated placeholder string derived from a module
    constant — no user data reaches the SQL text. Say so in a comment so a future reader does
    not mistake it for the injection pattern project rule 3 forbids.)
    ISO-format `created_at` on the way out.

    **`tests/unit/test_audit.py`** — fake `query`/`execute` bound into the module. Cover:
    `log_action` issues the INSERT with the three params; `log_action` swallows a raising
    `execute` and does not propagate; `list_operator_actions` passes every allowlist value plus
    the limit as parameters and its SQL contains `action IN (`; a row whose action is
    `order_created` (the customer-generated kind) is not requested by the query.
  </action>
  <verify>`python -m pytest tests/unit/test_audit.py -q` passes; `python -c "from app.services.audit import OPERATOR_ACTIONS; print(len(OPERATOR_ACTIONS))"` prints 18.</verify>

    - `GET /api/handoffs?status=active|resolved|all` (default `active`):
      ```sql
      SELECT h.id, h.phone, h.reason, h.status, h.assigned_to, h.created_at, h.resolved_at,
             h.metadata, COALESCE(c.name, '') AS customer_name
      FROM handoffs h LEFT JOIN customers c ON c.phone = h.phone
      [WHERE h.status = %s]
      ORDER BY (h.status = 'active') DESC, h.created_at DESC LIMIT 100
      ```
      Active first, then resolved newest-first — CONTEXT locks "resolved handoffs stay visible
      as recent history (active on top, resolved below)". ISO-format both timestamps. Add a
      `wa_link` field per row: `https://wa.me/{phone digits only}`.

    - `GET /api/handoffs/{handoff_id}`: the row above plus

      (`SELECT role, content, created_at FROM chat_history WHERE phone = %s ORDER BY created_at DESC LIMIT %s`,
      then reverse into chronological order — the same reversal `whatsapp_helpers.load_history`
      already does). Define `TRANSCRIPT_TURNS = 20` as a module constant. 404 if the handoff is
