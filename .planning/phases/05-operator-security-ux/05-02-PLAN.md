Wrap Supabase Auth in a single service module so the rest of the app never imports the
Supabase client for identity, and ship the one-off CLI that creates the two operator accounts
(aunt + admin) and performs admin-driven MFA recovery.

This plan owns identity verification only. It creates no routes, no templates, and does not
touch the opaque session store (plan 05-01, running in parallel). Plan 05-03 joins them.

Purpose: REQ-prod-auth-mfa — replace `password == Config.DASHBOARD_PASSWORD` with real
per-operator credentials plus TOTP, delegating password hashing and TOTP secret custody
entirely to Supabase Auth (never hand-roll either).
Output: `app/services/auth.py`, `scripts/manage_operators.py`, new config vars, a runbook.
</objective>

<task type="auto">
  <name>Task 2: app/services/auth.py — Supabase Auth wrapper</name>
  <files>app/services/auth.py</files>
  <action>
    Create `app/services/auth.py`. It is the ONLY module allowed to import `supabase` for
    identity purposes. Two client factories:
    `_anon_client()` -> `create_client(Config.SUPABASE_URL, Config.SUPABASE_ANON_KEY)` and
    `_admin_client()` -> `create_client(Config.SUPABASE_URL, Config.SUPABASE_KEY)`.
    Build a fresh client per call — these are short-lived request-scoped operations and a
    shared client would carry session state between operators.

    Public surface:

    ```python
    class AuthError(Exception): ...          # wraps AuthApiError; carries .code when available

    @dataclass(frozen=True)
    class AuthResult:
        user_id: str
        email: str
        is_admin: bool
        mfa_required: bool          # True when a VERIFIED totp factor exists and AAL is still aal1
        factor_id: str | None
        access_token: str
        refresh_token: str

    def sign_in(email: str, password: str) -> AuthResult
    def verify_totp(access_token, refresh_token, factor_id, code) -> str   # returns user_id
    def enroll_totp(access_token, refresh_token) -> dict     # {"factor_id","qr_code","secret"}
    def verify_enrollment(access_token, refresh_token, factor_id, code) -> None
    def admin_list_factors(user_id: str) -> list[dict]
    def admin_delete_all_factors(user_id: str) -> int
    def admin_create_user(email: str, password: str, role: str) -> str      # returns user_id
    def admin_list_users() -> list[dict]
    def send_password_reset(email: str) -> None
    ```

    CRITICAL — this is the single highest-value correctness rule in the phase (RESEARCH
    Pitfall 1): `sign_in_with_password` succeeds and returns a full session EVEN WHEN the user
    has a verified TOTP factor; it only reaches AAL1. `sign_in()` must therefore, after the
    password grant, call `client.auth.mfa.get_authenticator_assurance_level()` and
    `client.auth.mfa.list_factors()` and set
    `mfa_required = (a verified totp factor exists) and (aal.current_level != aal.next_level)`,
    plus `factor_id` = that factor's id. `sign_in()` must NEVER be treated by callers as
    "logged in" — it returns a *result*, and only 05-03's route layer decides whether to mint a
    session. Put that warning in the module docstring.

    `is_admin` = `user.app_metadata.get("role") == "admin"` (tolerate a missing/None
    app_metadata and default to False).

    `verify_totp` must rehydrate the AAL1 session on a fresh client
    (`client.auth.set_session(access_token, refresh_token)`) and then call
    `client.auth.mfa.challenge_and_verify({"factor_id": ..., "code": ...})`. Discard the
    returned AAL2 tokens — the app mints its own opaque session instead (05-01). Return the
    verified user's id.

    `enroll_totp` calls `client.auth.mfa.enroll({"factor_type": "totp", "issuer": "ALYASMEEN",
    "friendly_name": <email>})` after `set_session`; the returned `totp.qr_code` is already a
    `data:image/svg+xml;utf-8,...` URI usable straight in `<img src>` — do not re-encode it.

    `admin_delete_all_factors` uses the service_role client:
    `admin.auth.admin.mfa.list_factors({"user_id": uid})` then `delete_factor({"user_id": uid,
    "id": f.id})` per factor; returns the count deleted.

    `send_password_reset` calls `reset_password_for_email(email, {"redirect_to":
    f"{Config.DASHBOARD_BASE_URL}/login/reset"})`. Note in a comment that the installed client
    defaults to the PKCE flow, so the landing route receives a `?code=` query param that a
    server-rendered page can actually read (the implicit flow's URL fragment never reaches the
    server) — 05-09 builds that landing route.

    Never implement TOTP generation or verification yourself and never add `pyotp` — Supabase
    Auth is the system of record for which factors exist and are verified.

    Wrap every Supabase call in try/except and re-raise as `AuthError` with the original
    message and, when present, the provider `code` (so callers can special-case
    `over_email_send_rate_limit`). Log failures with the module logger but NEVER log the
    password, the TOTP code, the access token or the TOTP secret.
  </action>
  <verify>`python -c "import app.services.auth as a; print(sorted(n for n in dir(a) if not n.startswith('_')))"` lists AuthError, AuthResult, admin_create_user, admin_delete_all_factors, admin_list_factors, admin_list_users, enroll_totp, send_password_reset, sign_in, verify_enrollment, verify_totp; `grep -n "pyotp\|import supabase" app/services/auth.py` shows only the supabase import (no pyotp).</verify>
  <done>`app/services/auth.py` exposes the full surface above; `sign_in` performs the AAL check; admin operations use `Config.SUPABASE_KEY` and non-admin operations use `Config.SUPABASE_ANON_KEY`.</done>
