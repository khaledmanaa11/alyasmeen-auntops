  <name>Task 1: MFA enrollment routes + new-device admin alert</name>
  <files>app/routers/auth_routes.py</files>
  <action>
    Extend `app/routers/auth_routes.py`. All new routes below take
    `op: Operator = Depends(require_operator)` explicitly (these routes live on an unguarded
    router because `/login` shares it, so each protected route declares its own dependency).

    **Enrollment is assisted, never forced** (locked in CONTEXT): the QR is shown only on this
    explicit step, and nothing anywhere redirects an un-enrolled operator into it.

    A wrinkle to solve first: `auth_service.enroll_totp` needs a live Supabase AAL1
    access/refresh token pair, but the dashboard deliberately discards those after login (the
    opaque session is the source of truth). Resolve it the honest way — **re-authenticate for
    the enrollment step**: `POST /account/mfa/enroll` takes the operator's current password as a
    form field, calls `auth_service.sign_in(op.email, password)` to obtain a fresh token pair,
    and uses that. Re-asking for the password before a credential change is correct security
    behaviour anyway, and it avoids storing Supabase tokens for the life of a 30-day session.
    Document that reasoning in a comment.

    Routes:
    - `POST /account/mfa/enroll` (Form: `password`) ->
      `{"factor_id", "qr_code", "secret"}` from `auth_service.enroll_totp(...)`. Stash the
      access/refresh pair for the immediately-following verify step using
      `sessions.create_pending_login(...)` (the same single-use, 5-minute, server-side row the
      login flow uses — reuse it rather than inventing a second bridge) and return its token in
      an httpOnly cookie. On `AuthError` return 401 `{"detail": "كلمة المرور غير صحيحة"}`.
    - `POST /account/mfa/enroll/verify` (JSON: `{"code": "123456"}`) — consume the pending row,
      call `auth_service.verify_enrollment(...)`. On success:
      1. `sessions.revoke_all_for_user(op.user_id, except_session_id=op.session_id)` — CONTEXT
         locks "any credential change revokes ALL sessions"; keep the current one so she is not
         thrown out mid-enrollment. (Supabase's own client does an equivalent internal logout;
         this makes the app's opaque store agree instead of depending on Supabase's session
         bookkeeping.)
      2. `sessions.remember_device(...)` for the current device so she is not immediately
         challenged.
      3. `audit.log_action(op.email, "mfa_enrolled", {})`.
      4. Return `{"ok": true}`. On a bad code return 400 with an Arabic message and DO NOT
         revoke anything.
    - `GET /account/mfa/status` -> `{"enrolled": bool, "factors": n}` via
      `auth_service.admin_list_factors(op.user_id)`.

    **New-device alert.** In `POST /login/mfa` (and in the remember-device fast path of
    `POST /login`), plan 05-03 left a `# 05-09 fires the admin WhatsApp alert here` marker where
    `remember_device` returns `created=True`. Implement it now: when `created` is True and
    `Config.ADMIN_PHONE` is set, `queue_text(Config.ADMIN_PHONE, ...)` with a plain-Arabic
    sentence naming the operator's email, a trimmed user-agent and the time. Send it to the
    **admin only** — CONTEXT: "the aunt is not bothered". Use `queue_text` (the durable outbox),
    never a direct sender, and wrap in try/except so a notification failure can never block a
    login. Also `audit.log_action(email, "login_success", {"new_device": created})`, and log
    `login_failed` on the failure branches of `POST /login` and `POST /login/mfa`.
  </action>
  <verify>`python -m pytest -q` passes; `grep -n "ADMIN_PHONE\|revoke_all_for_user\|mfa_enrolled" app/routers/auth_routes.py` shows all three; in mock mode, log in from a fresh browser profile and confirm a new `outbox_jobs` row addressed to `ADMIN_PHONE` appears.</verify>
