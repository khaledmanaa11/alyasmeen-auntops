<objective>
Turn the dashboard API layer into something the aunt can actually operate: every mutation is
attributed in the audit trail, a status change that collides with a live bot conversation asks
her who wins instead of silently overwriting, and the alerts feed stops speaking in job IDs.

This plan owns `ui_api.py` and `processor.py` for the whole phase — it is the one place where
the operator-facing API semantics change. Plans 05-07 and 05-08 consume its payloads.

Purpose: success criteria 2 (conflicts, audit) and 4 (see and recover from failures).
Output: audit-logged mutations, a 409 conflict protocol, a reframed alerts payload, retry-all,
and proactive WhatsApp failure alerts.
</objective>

  <name>Task 1: Audit every mutation + bot-vs-aunt conflict guard on status change</name>
  <files>app/routers/ui_api.py, tests/integration/test_orders_api.py</files>
  <action>
    **Audit wiring.** Add `op: Operator = Depends(require_operator)` to the signature of every
    mutating endpoint in `ui_api.py` (`api_update_status`, `api_create_product`,
    `api_update_product`, `api_toggle_product`, `api_delete_product`,
    `api_retry_webhook_event`, `api_retry_outbox_job`, `api_broadcast_send`). The router-level
    dependency added in 05-03 already runs; FastAPI caches it per request, so naming it in the
    signature costs nothing and gives each handler `op.email`. After each successful mutation
    call `audit.log_action(op.email, "<action>", {...})` using the exact action names from
    `OPERATOR_ACTIONS` (05-05): `order_status_changed`, `product_created`, `product_updated`,
    `product_toggled`, `product_deleted`, `alert_retried`, `broadcast_sent`. Include the ids
    and the meaningful values in `details` (e.g. `{"order_id":.., "from":.., "to":..}`,
    `{"product_id":.., "name":..}`, `{"filter":.., "sent":.., "failed":..}`). `log_action` is
    already best-effort, so no extra try/except is needed at the call sites.

    **Conflict guard.** In `api_update_status`, after loading the order and BEFORE applying any
    change, call `handoff.bot_recently_active(phone)`. If it returns a dict and the request body
    does not contain `"force": true`, return a **409** with:
    ```json
    {"conflict": true, "reason": "bot_active", "customer_name": "...", "phone": "...",
     "last_activity": "<iso>", "requested_status": "ready",
     "message": "البوت يتحدث مع {name} الآن"}
    ```
    Use `JSONResponse(status_code=409, content=...)`, not `HTTPException`, so the body shape is
    exactly this (the UI in 05-08 branches on `conflict`).

    When `"force": true` IS present, the operator has chosen herself as the winner. Apply the
    status change as normal AND:
    1. `execute("UPDATE sessions SET paused = TRUE WHERE phone = %s", (phone,))` — she is taking
       over the conversation, so the bot must stop replying.
    2. `execute("INSERT INTO handoffs (phone, reason, status, assigned_to) VALUES (%s, %s, 'active', 'aunt')", (phone, "operator_takeover"))`
       so the takeover shows up in the handoffs tab and she has an explicit "return to bot"
       button to undo it.
    3. `audit.log_action(op.email, "order_status_conflict_override", {...})` in addition to the
       normal `order_status_changed` row.

    Write a comment explaining why this is a heuristic and not a lock (see 05-05 Task 1): the
    collision being solved is one human versus one bot on a 10-30 orders/day shop.

    **Tests** — extend `tests/integration/test_orders_api.py`: a status change with no recent
    bot activity still returns 200 (regression); with `bot_recently_active` monkeypatched to
    return a dict it returns 409 and `body["conflict"] is True` and NO order UPDATE was issued;
    with `{"status":"ready","force":true}` it returns 200, issues the `paused = TRUE` update and
    the handoffs INSERT; and a successful status change produces an
    `order_status_changed` audit call (assert against a monkeypatched `log_action` spy).
  </action>

<task type="auto">
  <name>Task 2: Alerts API rework — plain-Arabic action payload + retry-all</name>
  <files>app/routers/ui_api.py, tests/integration/test_alerts_api.py</files>
  <action>
    Rewrite the Alerts section of `ui_api.py`. The current payload
    (`{"webhook_events": [...], "outbox_jobs": [...]}` with raw `attempts`/`last_error`/`kind`)
    tells the aunt nothing actionable. CONTEXT locks: action-oriented plain Arabic cards naming
    the customer, technical detail collapsed behind a details toggle.

    **`GET /api/alerts`** now returns:
    ```json
    {"alerts": [ ... ], "counts": {"total": n, "customer_facing": n, "internal": n}}
    ```
    Each alert item:
    ```json
    {"id": "...", "source": "webhook_event" | "outbox_job",
     "phone": "...", "customer_name": "فاطمة",
     "severity": "customer_facing" | "internal",
     "headline": "تحتاج انتباهك الآن",
     "what_happened": "رسالة لم تصل إلى فاطمة",
     "what_to_do": "تابعي المحادثة معها في واتساب",
     "wa_link": "https://wa.me/972...",
     "kind": "whatsapp_message", "attempts": 3, "max_attempts": 3,
     "error": "<raw technical text>", "payload": {...}, "created_at": "<iso>"}
    ```
    Keep both existing queries but add `LEFT JOIN customers c ON c.phone = <table>.phone` and
    select `COALESCE(c.name, '') AS customer_name`. Build the Arabic framing in a private
    `_frame_alert(row, source) -> dict` helper so the template stays purely presentational, and
    so the phrasing lives in one place. Phrasing rules (the aunt's own words drive these):
    - outbox `whatsapp_message` / `whatsapp_buttons` -> severity `customer_facing`,
      what_happened `"رسالة لم تصل إلى {name}"`, what_to_do
      `"تابعي المحادثة معها في واتساب"`.
    - outbox `pdf_invoice` -> `customer_facing`, `"الفاتورة لم تصل إلى {name}"`,
      `"أعيدي المحاولة أو أرسليها يدوياً"`.
    - webhook_event dead-letter -> `customer_facing`,
      `"رسالة من {name} لم تُقرأ من النظام"`, `"افتحي المحادثة وشوفي شو بدها"`.
    - anything else -> `internal`, `"فشلت عملية داخلية ({kind})"`,
      `"أعيدي المحاولة، وإذا تكررت راجعي خالد"`.
    When the customer name is empty, fall back to the phone number inside the sentence — never
    render an empty name into Arabic text. `wa_link` = `https://wa.me/` + digits of the phone.

    **`POST /api/alerts/retry_all`** — NEW. Resets every dead-lettered `webhook_events` row
    (`processed = FALSE, attempts = 0, error = NULL` where the current dead-letter predicate
    matches) and every permanently-failed `outbox_jobs` row (`status = 'pending', attempts = 0,
    last_error = NULL, updated_at = now()` where `status='failed' AND attempts >= max_attempts`)
    in two statements — not a per-row loop. Return
    `{"ok": true, "webhook_events": n, "outbox_jobs": n}` using counts read immediately before
    the updates. Audit as `alert_retry_all`. This is the post-outage recovery button CONTEXT
    asks for, alongside the existing per-item retries (keep both).

    **Tests** — rewrite `tests/integration/test_alerts_api.py` against the new shape: the
    response has `alerts` and `counts`; a failed `whatsapp_message` job for a known customer
    produces `severity == "customer_facing"` and a `what_happened` containing that customer's
    name; a job for an unknown phone falls back to the number and does not contain `"إلى "` with
    an empty name; `wa_link` is present; the raw `error`/`payload`/`attempts` fields survive for
    the details toggle; `retry_all` issues exactly two UPDATE statements and returns both counts;
    the existing per-item retry tests still pass (adjusted only for the fixture rename).
  </action>
  <verify>`python -m pytest tests/integration/test_alerts_api.py -q` passes; `python -c "import app.routers.ui_api as m; print(hasattr(m,'_frame_alert'))"` prints True; `python -m pytest -q` full suite green.</verify>
  <done>`GET /api/alerts` returns framed, customer-named, severity-tagged action items with the technical fields retained, and `POST /api/alerts/retry_all` bulk-resets both tables.</done>

<task type="auto">
  <name>Task 3: Proactive WhatsApp alerts on permanent failure</name>
  <files>app/services/processor.py, tests/unit/test_processor.py</files>
  <action>
    Today a permanently-failed outbox job and a dead-lettered webhook event are only visible if
    someone opens `/alerts`. CONTEXT locks proactive WhatsApp alerts to BOTH: the aunt gets
    customer-facing failures, Khaled gets everything.

    Add to `app/services/processor.py`:
    ```python
    CUSTOMER_FACING_KINDS = {"whatsapp_message", "whatsapp_buttons", "pdf_invoice"}

    def notify_permanent_failure(source: str, phone: str, kind: str, error: str) -> None
    ```
    Behaviour:
    1. Resolve the customer name: `SELECT name FROM customers WHERE phone = %s`, falling back to
       the phone.
    2. **Loop guard (mandatory):** if `phone` equals `Config.AUNT_PHONE` or `Config.ADMIN_PHONE`,
       return immediately without notifying. A failed alert-to-the-aunt that itself queues an
       alert-to-the-aunt is an infinite outbox loop. Say so in a comment.
    3. If `kind in CUSTOMER_FACING_KINDS` (or `source == "webhook_event"`) and
       `Config.AUNT_PHONE` is set -> `queue_text(Config.AUNT_PHONE, <plain Arabic sentence
       naming the customer and what to do>)`.
    4. If `Config.ADMIN_PHONE` is set -> `queue_text(Config.ADMIN_PHONE, <same, plus kind and
       the truncated error>)`.
    5. Wrap the whole body in try/except + structlog warning — a failing notification must never
       change the outcome of the job that failed.

    Use `queue_text` (the outbox), never `send_text` directly: the outbox is the single send
    path for everything except `process_job` itself and the standalone scheduler services.

    Call sites:
    - `process_job`'s `except` branch: after the `status = 'failed'` UPDATE, call
      `notify_permanent_failure("outbox_job", phone, kind, str(e))` **only when this attempt was
      the last one**. `attempts` is already a parameter but `max_attempts` is not selected — add
      `max_attempts` to the `SELECT` in `process_outbox_jobs`, pass it through to `process_job`
      as a new parameter (default 3 so existing callers/tests keep working), and gate on
      `attempts + 1 >= max_attempts`.
    - `process_webhook_events`' dead-letter branch (where it already writes
      `error = 'dead-letter: ...'`): call
      `notify_permanent_failure("webhook_event", ev["phone"], "inbound_message", str(e))`.

    **Tests** — extend `tests/unit/test_processor.py`: a job that fails on its final attempt
    queues exactly two outbox rows addressed to `AUNT_PHONE` and `ADMIN_PHONE`; a job that fails
    on a non-final attempt queues none; a failure whose `phone` IS `AUNT_PHONE` queues none (the
    loop guard); a non-customer-facing kind queues only the admin row; a dead-lettered webhook
    event notifies both. Set `Config.AUNT_PHONE`/`ADMIN_PHONE` via monkeypatch on the names bound
    into `app.services.processor`.
  </action>
  <verify>`python -m pytest tests/unit/test_processor.py -q` passes; `grep -n "send_text(Config" app/services/processor.py` returns nothing (alerts must go through the outbox); `python -m pytest -q` full suite green.</verify>
  <done>Permanent failures push a plain-Arabic WhatsApp alert to the aunt (customer-facing) and the admin (everything) through the outbox, exactly once, with an infinite-loop guard.</done>
