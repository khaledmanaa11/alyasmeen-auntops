# ALYASMEEN Knowledge Vault

A personal knowledge base maintained by Claude Code.
Based on Andrej Karpathy's LLM Wiki pattern, extended with a graphify graph layer.

## Purpose

This vault is a structured, interlinked knowledge base for the **ALYASMEEN AuntOps**
project — a WhatsApp ordering bot for a natural & handmade skincare business in Palestine
(lotions, creams, candles). It captures the codebase, the business, and the decisions
behind both.

Claude maintains the vault. The human (Khaled) curates sources, asks questions, and guides
the analysis. The goal is a knowledge base that compounds over time as the project grows.

## The three layers

This vault sits on top of two layers beneath it. Knowledge flows **upward**: code is the
ground truth, graphify extracts its structure, and the wiki turns that structure into
human-meaningful prose.

| Layer | Lives in | Built by | Nature |
|-------|----------|----------|--------|
| **1. Code** | `../app/`, `../tests/` | Khaled + Claude | Ground truth — the running system |
| **2. Graph** | `../graphify-out/` → mirrored in `graph/` | graphify (automated) | Structural skeleton — entities, edges, communities, god nodes |
| **3. Wiki** | `wiki/` | Claude (curated) | Semantic layer — cited prose, navigable in Obsidian |

- **Layer 1 (Code)** never lies but is hard to navigate. Always verify claims against it.
- **Layer 2 (Graph)** is regenerated by running graphify; it is *discovery*, not truth.
  Treat `graph/` as read-only — never hand-edit it; re-sync it instead (see below).
- **Layer 3 (Wiki)** is where understanding is written down and curated by hand.

Obsidian's graph view renders layers 2 and 3 together: graphify's `[[community]]` hubs and
the wiki's `[[concept]]` pages link into one navigable space.

## Folder structure

```
raw/          -- source documents (immutable -- never modify these)
graph/        -- Layer 2 mirror: graphify output rendered as Obsidian notes (auto-generated, read-only)
wiki/         -- Layer 3: markdown pages maintained by Claude
wiki/index.md -- master Map of Content for the whole vault
wiki/log.md   -- append-only record of all operations
```

Sources to drop into `raw/` include: code files and modules, the project `CLAUDE.md`,
graphify report snapshots, schema dumps, the agent eval dataset, WhatsApp transcripts,
design notes, and business decisions.

## Graph layer (graphify integration)

graphify analyzes the codebase and produces `../graphify-out/` (graph.json, GRAPH_REPORT.md,
graph.html). It already emits Obsidian-style `[[wiki-links]]`, which makes it the natural
middle layer between code and the wiki.

**Re-syncing the graph layer** — after re-running graphify on the project:

1. Copy the fresh `GRAPH_REPORT.md` into `raw/graphify-report-snapshot.md`
2. Regenerate `graph/graph-overview.md` from it (stats, community hubs, god nodes,
   surprising connections, hyperedges, import cycles)
3. Append a `log.md` entry noting the new node/edge/community counts
4. Re-check wiki pages: any concept whose graphify community changed may need updating

**Using the graph to grow the wiki** — the graph tells you *what to write about*:

- **God nodes** = the core abstractions. Each deserves a wiki page.
- **Communities** = concept clusters. Each maps to one wiki concept page.
- **Surprising connections** = non-obvious links worth a note or a callout.
- **Hyperedges** = multi-node relationships; capture them as "## How it fits together"
  sections that link the involved pages.

Every wiki concept page should link **down** to its graphify community
(`[[graph-overview#Community ...]]`) so the reader can drop from prose into raw structure.

## graphify → wiki ingest workflow

When the user asks you to ingest a source from `raw/` (or to mine the graph for new pages):

1. Read the full source document (and the relevant `graph/` community for structure)
2. Discuss key takeaways with the user before writing anything
3. Create a summary page in `wiki/` named after the source or concept
4. Create or update concept pages for each major idea or entity the graph surfaced
5. Add wiki-links ([[page-name]]) to connect related pages, and link down to the graph layer
6. Update `wiki/index.md` with new pages and one-line descriptions
7. Append an entry to `wiki/log.md` with the date, source name, and what changed

A single source may touch 10-15 wiki pages. That is normal.

## Page format

Every wiki page should follow this structure:

```markdown
# Page Title

**Summary**: One to two sentences describing this page.

**Sources**: List of raw source files / code paths this page draws from.

**Graph**: Link to the graphify community/god-node this page synthesizes.

**Last updated**: Date of most recent update.

---

Main content goes here. Use clear headings and short paragraphs.

Link to related concepts using [[wiki-links]] throughout the text.

## Related pages

- [[related-concept-1]]
- [[related-concept-2]]
```

## Citation rules

* Every factual claim should reference its source file or code path
* Use the format (source: filename) after the claim — e.g. (source: app/routers/whatsapp.py)
* Graph-derived claims should be marked — e.g. (graph: god node `query()`, 40 edges)
* If two sources disagree, note the contradiction explicitly
* If a claim has no source, mark it as needing verification
* When a claim depends on live state (Supabase data, Meta review status, env vars),
  mark it as time-sensitive and date it

## Question answering

When the user asks a question:

1. Read `wiki/index.md` first to find relevant pages
2. Read those pages and synthesize an answer
3. If structure is unclear, drop to `graph/graph-overview.md` for the raw connections
4. Cite specific wiki pages in your response
5. If the answer is not in the vault, say so clearly
6. If the answer is valuable, offer to save it as a new wiki page

Good answers should be filed back into the wiki so they compound over time.

## Lint

When the user asks you to lint or audit the vault:

* Check for contradictions between pages
* Find orphan pages (no inbound links from other pages)
* Identify concepts mentioned in pages that lack their own page
* Cross-check against the graph: god nodes and named communities with no wiki page are gaps
* Flag claims that may be outdated based on newer sources (especially time-sensitive ones
  like deployment status, Meta WABA review, or env-var configuration)
* Flag any wiki page whose `graph/` link is stale after a graph re-sync
* Check that all pages follow the page format above
* Report findings as a numbered list with suggested fixes

## Rules

* Never modify anything in the `raw/` folder
* Never hand-edit `graph/` — it is a generated mirror; re-sync it from graphify instead
* Always update `wiki/index.md` and `wiki/log.md` after changes
* Keep page names lowercase with hyphens (e.g. `whatsapp-bot-brain.md`)
* Write in clear, plain language
* Arabic text in sources is intentional — preserve it; translate inline when it aids clarity
* This vault documents the project; it is not the running code. Never treat wiki notes as a
  substitute for the live source in `../app/` — verify against code before acting on it
* When uncertain about how to categorize something, ask the user
